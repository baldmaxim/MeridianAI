# Добавление пользователя в VPN (Remnawave)

**Обычный сценарий — бот `@YCTraffic_BOT`:** кнопка «➕ Новый юзер» → ответить на 4 вопроса (имя, срок,
лимит, сквад) → «✅ Да» → бот создаёт юзера в панели и присылает ссылку подписки + QR.
Одной строкой: `/add имя [дней=30] [ГБ=0] [сквад=External]`.
Запасной путь — панель: создать юзера и включить в сквад `External` (единственный; `Home` удалён 31.08.2026).
Дальше всё подхватывается автоматически в течение ~5 минут.

Так сделано потому, что все 4 хоста подписки идут на **один вход — YC-релей
`89.169.191.175`**, а панель пушит клиентов только remnanode-нодам (Kamatera).
YC-релей — нативный xray с ручным конфигом, его закрывает синк.

## Что работает автоматически

| Где | Что делает | Механизм | Логи |
|---|---|---|---|
| YC-релей | клиенты на 4 VLESS-инбаундах + персональные плечи `out-nl-<user>` + правила роутинга | `xray-sync-users.timer` (5 мин) → `/usr/local/bin/xray-sync-users.py` | `journalctl -u xray-sync-users` |
| Kamatera | клиенты на ноде | сама панель (remnanode) | — |

Скрипт синка:

- берёт список из API панели (`GET /api/users`), токен в `/etc/xray-sync/token` (root, 0600);
- доступ даёт **только юзерам со статусом `ACTIVE` и хотя бы одним сквадом** — снятие галки
  или `DISABLED`/`EXPIRED` в панели убирает клиента с релея тем же таймером;
- идемпотентен: конфиг переписывается и xray рестартится **только при реальном изменении**,
  перед применением всегда `xray -test`;
- при пустом/битом ответе API конфиг не трогает, за один прогон не удаляет больше трети
  клиентов инбаунда;
- значения uuid не печатает и не логирует.

Исходник в репозитории: [`xray-sync-users.py`](xray-sync-users.py).

## Диагностика: «подключается и сразу отключается» / «не пингуется ни один сервер»

Все хосты подписки — один вход, поэтому «мертвы все профили» ничего не говорит о том,
чья сторона виновата. Порядок проверки — сверху вниз, первая же строка обычно закрывает вопрос.

| Симптом | Проверка | Причина |
|---|---|---|
| Мертвы все профили, само чинится за ~5 мин | `ssh yc "uptime; sudo journalctl --list-boots \| tail -3"` — стоп ровно на boot+24 ч | **суточный стоп прерываемой ВМ** — так и задумано, см. ниже |
| Мертвы все профили, на релее **нет ни одной** строки по юзеру | `ssh yc 'sudo journalctl -u xray --since "-1h" \| grep "email: <user>"'` → пусто, а у других юзеров строки есть | до входа не дошло: оператор/DPI или второй туннель на телефоне — сервер не при чём |
| На релее есть reject / `REALITY` / handshake-ошибки | тот же grep без фильтра по `accepted` | Reality: чужой uuid (синк) или отвалился `dest` |
| Новый юзер — мертвы все хосты | `journalctl -u xray-sync-users`, запустить руками | не отработал синк релея |
| Нода красная в панели, но трафик идёт | — | нет/лежит remnanode-агент на :2222 |
| Рвётся у всех, вперемешку, без ошибок в логах релея | на выходной ноде `dmesg -T \| grep "table full"`, `sysctl -n net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max` | переполнение conntrack на выходе — пакеты молча дропаются |
| Юзер отключён панелью | `GET /api/users` → `status`, `activeInternalSquads` | `DISABLED`/`EXPIRED`/снят сквад → синк убрал клиента с релея |

Чеклист на телефоне (INCY), когда сервер живой:

- обновить подписку в приложении (профиль мог остаться со старым uuid);
- выключить второй VPN — на iOS активен **только один** туннель, включённый OpenVPN
  (NAS на той же YC-ВМ) глушит INCY на всех серверах;
- переключиться на XHTTP `6443` или gRPC `9444` — обход DPI, который режет `:443`;
- проверить с Wi-Fi: если там работает, виноват мобильный оператор, а не релей.

## Conntrack на выходной ноде (Kamatera)

Через выход идёт ~87 % трафика, а дефолты ядра там выведены из 957 МБ RAM: было
`nf_conntrack_max = 7680` и `tcp_timeout_established = 432000` (5 суток). 19.08.2026 таблица
переполнилась — 190 строк `nf_conntrack: table full, dropping packet`, это рвёт туннели у всех
сразу и в логах xray никак не видно.

Поднято до `65536` записей (~21 МБ RAM), hashsize `16384`, established-таймаут — 1 час,
остальные TCP-таймауты 30 с: `/etc/sysctl.d/99-conntrack.conf` + `/etc/modprobe.d/nf_conntrack.conf`.

```bash
ssh kamatera "sysctl -n net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max"
ssh kamatera "dmesg -T | grep -c 'table full'"   # новые вхождения = снова мало, поднимать дальше
```

## Мониторинг входа релея

Пробник живёт на **Kamatera** (`ssh kamatera`), не на релее и не на Selectel: релей не может
проверять сам себя, а с Selectel недоступен `api.telegram.org`.

| Что | Где |
|---|---|
| скрипт | `/usr/local/bin/relay-probe.py` (исходник — [`relay-probe.py`](relay-probe.py)) |
| таймер | `relay-probe.timer`, каждые 3 мин (юниты — [`relay-probe.service`](relay-probe.service), [`relay-probe.timer`](relay-probe.timer)) |
| состояние | `/var/lib/relay-probe/state.json` |
| секреты | `/etc/relay-probe/tg.env` (root, 0600) |
| история | `journalctl -u relay-probe` |

Кроме портов пробник поднимает **настоящий VLESS-туннель**: служебный юзер `RelayProbe`
(сквад External, создан 25.08.2026), его подписка — в `/etc/relay-probe/probe.env`, бинарь
`xray-probe` вынут из контейнера ноды (`docker cp remnanode:/usr/local/bin/xray`). Проба
поднимает socks на `127.0.0.1:10999`, курлит `api.ipify.org` и ждёт выход `194.37.81.38`.
Это отличает «порт открыт, но туннель мёртв» от реального обрыва.

Алерт — после 3 неудачных прогонов подряд (≈9 мин), чтобы штатный суточный стоп ВМ не
давал ложную тревогу каждый день.

Проверяет 5 входов: `443` полным TLS-хендшейком с SNI `www.apple.com` (подтверждает сразу

## Бот (@YCTraffic_BOT)

Кнопки под полем ввода (появляются после `/start`). Любое изменение в панели — только после
inline-подтверждения «✅ Да»; кнопка живёт 10 мин.

| Кнопка / команда | Что делает |
|---|---|
| 📊 Сводка (`/stat`, «стат») | входы + туннель сейчас, обрывы 24 ч/7 дн, ноды, юзеры, выходная нода |
| 🔍 Проверить сейчас (`/check`) | только 5 входов релея и сквозной туннель (~10 с) |
| 👥 Юзеры (`/users`) | по строке на юзера: 🟢 онлайн (<5 мин) / ⚪ был N назад / ❌ DISABLED·без сквада, трафик, срок (⚠️ <7 дн) |
| 📜 Обрывы (`/outages`) | эпизоды простоев за 7 дней с длительностью; ~5-минутные «мертво всё» помечены как суточный стоп ВМ |
| 📈 Трафик YC (`/traffic`) | готовый отчёт с релея по ssh: платный исходящий YC (без CDN) из 100 ГБ и CDN из пакета 150 ГБ — остаток, прогноз; топ-5 юзеров по трафику из панели |
| 🖥 Нода (`/node`) | conntrack, load, память, аптайм, контейнеры, счётчик `table full` |
| ➕ Новый юзер (`/add`) | опросник: имя текстом → срок (30/90/180/365/10 лет/свой) → лимит (без/50/100/200/500 ГБ/свой) → сквад (кнопки из панели) → «✅ Да» → карточка + ссылка подписки + QR. Любая команда/кнопка прерывает опросник, живёт 10 мин |
| `/add имя [дней=30] [ГБ=0] [сквад=External]` | то же одной строкой, без опросника |
| 📖 Инструкция (`/help`, `/start`) | полная памятка: кнопки, команды, кнопки карточки, сценарии («подключить человека», «не работает», «продлить»), что приходит само |
| `/user <имя>` | карточка + **готовый диагноз** + кнопки: 🔴/🟢 вкл-выкл, 📅 +30 дней, ♻️ сброс трафика, 🔗 подписка (+QR), 📱 устройства (HWID) |

**Жалоба «не работает» — первый шаг: `/user <имя>` в боте**, потом таблица диагностики выше.

Само приходит (проверка раз в 10 мин, состояние `/var/lib/relay-probe/watch.json`, первый прогон
только запоминает): нода в панели пропала/вернулась, юзер впервые подключился, срок истекает ≤3 дн
(с кнопкой «+30 дней») и истёк, трафик ≥90 % лимита (с кнопкой сброса), новые `table full` в conntrack.

| Что | Где |
|---|---|
| демон | `/usr/local/bin/relay-bot.py` (long polling, webhook невозможен — :443 занят xray) |
| юнит | `relay-bot.service` (Restart=always, MemoryMax=128M) |
| история прогонов | `/var/lib/relay-probe/runs.jsonl` — по строке на прогон пробника |
| доступ к панели | `/etc/relay-probe/panel.env` (`PANEL_URL`, `PANEL_TOKEN`, 0600) — админский, им же идут мутации |
| трафик YC | ключ `/etc/relay-probe/yc_key` → `ubuntu@89.169.191.175`, в `authorized_keys` на YC с `command="/usr/local/bin/yc-traffic-report.py --dry-run",no-pty,...` (ничего кроме отчёта не выполнит; с 28.09.2026, раньше был голый vnstat) |
| QR | `qrencode` (apt), ссылка идёт в stdin, не в argv |
| проверка руками | `ssh kamatera "/usr/local/bin/relay-bot.py --stat"` (также `--check`, `--users`, `--outages`, `--traffic`, `--node`, `--user <имя>`, `--watch-once`) |
| обновить | `scp docs/relay-bot.py kamatera:/usr/local/bin/ && ssh kamatera "systemctl restart relay-bot"` |

Служебный `RelayProbe` в списках скрыт. Ссылка подписки — секрет доступа: уходит только в
`TG_CHAT_ID` по кнопке и не логируется. Панель кладёт `onlineAt`/трафик в `userTraffic`, не в корень
юзера — бот их поднимает (`flatten_user`).

Гоча curl: config-файл читается **построчно**, поэтому многострочный текст обязан уезжать
с escape-последовательностью перевода строки — иначе в Telegram улетает только первая строка
(на этом попались трижды: алерты, сводка, дайджест трафика). Функция `esc()` во всех скриптах
это делает; токен по-прежнему идёт в curl через stdin, не через argv.

Бот отвечает только в чат из `TG_CHAT_ID` — на чужие сообщения и callback'и молчит. Он же забирает
апдейты, поэтому `relay-probe.py --find-chat` после его запуска ничего не покажет:
чтобы сменить чат, сначала `systemctl stop relay-bot`.

## Stream-лог релея: кто как рвётся

На релее включён `access_log /var/log/nginx/stream-sni.log` в `stream.d/yc-split.conf`
(logrotate: 3 дня / 20 МБ). Формат: `время IP sni= up= sess= status= sent= recv=`.
Это единственное место, где видно **время жизни каждой сессии** и куда её отдал `ssl_preread`.

Как читать при жалобе «рвётся»:

```bash
ssh yc "sudo grep '<IP клиента>' /var/log/nginx/stream-sni.log | tail -20"
```

- `sni="www.apple.com" up=127.0.0.1:8443` — норма; `up=...8444` = профиль с чужим SNI ушёл в сайты;
- `sess≈0.1 recv≈104 sent≈6.4К` — клиент открыл TLS без Reality-авторизации и закрыл: это
  ping/latency-проба приложения (Happ/INCY так мерит задержку), десятки в минуту = клиент
  крутится в цикле переподключений;
- `recv > 1000` — рабочая сессия с трафиком.

Сверять с релейным xray: `sudo journalctl -u xray --since "-15m" | grep "email: <user>"` —
если в минуты жалобы `accepted` нет, а stream-лог полон коротких проб, туннель у клиента
не поднимался. Одновременно смотреть `journalctl -u relay-probe` на Kamatera: если там
туннель в те же минуты живой, проблема на стороне телефона/оператора, а не на сервере.

## Суточный стоп релея — это норма

ВМ релея — **прерываемая** (`scheduling_policy.preemptible: true`, ВМ `epda7gdqku2o4rdhgie2`,
папка `b1glmcmiqgufcko1627a`), YC гасит такие через ≤24 ч работы. Поднимает обратно своя
функция **`vm-autostart`** с таймер-триггером `vm-autostart-timer`, крон `0/5 * * * ? *`,
поэтому простой ~5 мин раз в сутки, а окно уезжает вперёд на ~5 мин/сут (стоп = boot+24 ч).
Так сделано осознанно, ради цены — не чинить.

Следствия, о которых надо помнить:

- в это окно у **всех** юзеров VPN «подключается и сразу отключается» — сервер вернётся сам;
- если решим убрать: `yc compute instance stop --id epda7gdqku2o4rdhgie2` →
  `... update --id ... --preemptible=false` → `... start ...` (профиль `default`);
  сократить простой без снятия флага — крон триггера на `0/1 * * * ? *`.

## Трафик YC (100 ГБ/мес бесплатно)

Через релей идёт весь трафик подписки, а у Yandex Cloud тарифицируется исходящий сверх
100 ГБ в месяц. Учёт: `vnstat` на YC + `yc-traffic-report.py`.

- ежедневный дайджест — `yc-traffic-report.timer` (09:00 МСК)
- пороги 70/90/100 ГБ — `yc-traffic-alert.timer` (раз в час, `--check-only`)
- вручную: `ssh yc "vnstat -m"` или `sudo /usr/local/bin/yc-traffic-report.py --dry-run`
- vnstat стоп ВМ переживает (база с 24.08.2026), месячный счётчик полный

**CDN в отчёте (с 28.09.2026).** Трафик релей→CDN vnstat видит как обычный исходящий, а Яндекс
его не тарифицирует, поэтому отчёт вычитает его из «платного» и показывает отдельным блоком против
пакета CDN 150 ГБ (сверх — 1,054 ₽/ГБ, алерт при 150). Источник — `stream-sni.log`: сессии с
`sni="static.meridianai.ru"` приходят только с узлов CDN, их `sent` = отдача в CDN. Скрипт под root
(оба таймера) суммирует по дням в `/var/lib/yc-traffic/cdn.json` (0644, 62 дня); логи живут 14 дней,
день берётся максимумом, так что ротация сумму не уменьшит. Бот под ubuntu логи не читает — только этот файл.

Готча: **api.telegram.org с YC напрямую недоступен**, поэтому скрипт шлёт через локальный
socks-вход самого релея (`127.0.0.1:10808` → выходная нода), с фолбэком на прямой запрос.

Секреты бота — в `/etc/xray-sync/tg.env` (root, 0600), формат:

```
TG_BOT_TOKEN=<токен от @BotFather>
TG_CHAT_ID=<id чата>
```

`sudo /usr/local/bin/yc-traffic-report.py --find-chat` покажет chat_id из апдейтов бота
(токен при этом не печатается).

## LTE с белыми списками: вход через Yandex Cloud CDN (25.09.2026)

МегаФон (Ковров/Владимир) в режиме белых списков режет IP релея `89.169.191.175`: сервер шлёт
ServerHello, ответ до телефона не доходит (в `stream-sni.log` сигнатура `sent≈6.4К recv<100`,
в xray ноль строк). Адреса CDN Яндекса пропускаются, поэтому для таких мест есть отдельный вход:

```
Happ ─TLS/h2 SNI static.meridianai.ru─▶ CDN 188.72.103.4 (ourcdn) ─HTTPS─▶ o.meridianai.ru
     ─▶ nginx stream :443 → 127.0.0.1:8444 (conf.d/cdn-origin.conf) ─/s/<path>─▶ xray in-cdn 127.0.0.1:8446
     ─▶ out-nl-<user> (Kamatera)
```

| Что | Где |
|---|---|
| CDN-ресурс | `bc8rrcgrfptgloufoivx`, cname `static.meridianai.ru`, origin-группа `meridian-origin` → `o.meridianai.ru` (HTTPS), кэш выкл., Host = `static.meridianai.ru` |
| Сертификат CDN | Certificate Manager `fpqbljntlvplovj4i7lp` (LE, авто-продление через CNAME `_acme-challenge.static`) |
| Сертификат origin | certbot на релее, `/etc/letsencrypt/live/o.meridianai.ru/` |
| Вход xray | `in-cdn`: vless + xhttp `packet-up`, `uplinkHTTPMethod GET`, `serverMaxHeaderBytes 65536`, клиенты ведёт синк (группа в `GROUPS`) |
| Панель | профиль `RELAY_CDN` (без ноды), инбаунд `CDN_VLESS_XHTTP`, сквад `Kovrov` (бывш. `CDN_LTE`), хосты `🇷🇺 [KOVROV] CDN` и `🇷🇺 [KOVROV] YC` |
| DNS Selectel | A `o` → 89.169.191.175; CNAME `static` → `aa9b9cffb99a3607.topology.gslb.yccdn.ru.`; CNAME `_acme-challenge.static` → `fpqbljntlvplovj4i7lp.cm.yandexcloud.net.` |

Почему настроено именно так (всё проверено на телефоне):
- **адрес хоста — IP `188.72.103.4`, а не домен**: по LTE Happ не резолвил `static.meridianai.ru`;
  имя остаётся в SNI и `host`. Если Яндекс сменит anycast-IP (`dig +short static.meridianai.ru`) — поменять `address` хоста;
- **`uplinkDataPlacement: header`**: узел CDN внутри сети МегаФона (`85.26.163.217`) не пропускает
  тело GET, POST ресурс CDN не разрешает; поэтому данные вверх идут в заголовках `X-Data-*`;
- **`serverMaxHeaderBytes 65536`** на `in-cdn` и `large_client_header_buffers 8 16k` в vhost: по умолчанию
  xray режет заголовки больше 8 КБ ответом 431;
- **`X-Accel-Buffering: no`** в location — без него CDN буферизует ответ и скорость падает до ~1.6 Мбит/с.

Доступ: только юзеры в скваде `Kovrov` (панель → пользователь → сквады External + Kovrov).

Второй хост **`🇷🇺 [KOVROV] YC`** — тот же вход `in-cdn`, но прямо на релей без CDN: `89.169.191.175:443`,
SNI/host `o.meridianai.ru`, `alpn http/1.1` (nginx 8444 без h2), данные в теле GET (`uplinkHTTPMethod GET`).
Зачем: Wi-Fi «КовровТелеком» с 25.09.2026 режет Reality с SNI `www.apple.com` (TCP есть, ClientHello не доходит,
в `stream-sni.log` `sni="" up=- sess=30 recv=0`), а наш домен на тот же IP пропускает. На LTE МегаФона не
работает (IP режется) — там только CDN. Плюс без CDN нет 60-секундного обрыва простаивающих соединений:
CDN закрывает запрос к origin после 60 с без данных, xray не шлёт keepalive в downlink packet-up, поэтому
Telegram/push через CDN переподключаются. Трафик этого хоста идёт в исходящий релея (100 ГБ), CDN — в пакет CDN.
Деньги: 150 ₽/мес (пакет 150 ГБ), сверх — 1,054 ₽/ГБ; трафик релей→CDN Яндекс не тарифицирует.
Экранирование источников и выгрузку логов CDN **не включать** (3 843 и 5 490 ₽/мес).

Диагностика: в `conf.d/cdn-origin.conf` раскомментировать `access_log ... xhttp_diag` у location туннеля —
видно `xff` (IP телефона), узел CDN (`rip`), загрузки (`/<session>/<seq>`) и их статусы.
